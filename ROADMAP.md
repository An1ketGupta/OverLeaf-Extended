## 2. Product scope

Build an online LaTeX workspace with AI-assisted editing and explainable resume compatibility/job-description analysis.

### First release

- Accounts, private projects, text files/assets, autosave, and immutable source snapshots.
- LaTeX editing, compilation through the route validated in Part 0A, diagnostics, PDF preview, and PDF/source download.
- A small set of curated resume and general-document templates verified against the chosen compiler.
- AI explanations, LaTeX generation, selected-text edits, and compile-error assistance.
- Reviewable AI diffs, explicit apply/reject, stale-edit protection, and restore.
- Resume analysis from an uploaded PDF or the exact PDF generated by the selected compiler.
- Extracted-text preview, contact/section detection, readability/completeness findings, and evidence-backed job matching.
- Separate internal compatibility estimates, job-requirement coverage, and writing suggestions.

### Follow-on features already discussed

Structured resume forms, shared-profile variants, layout assistance, application snapshots, visual PDF comparison, and research submission checks are sequenced in Part 9. They remain planned follow-on work.

Real-time coediting, payments, public marketplaces, OCR, arbitrary remote imports, and automated web research are outside the first release.

### Product rules

1. Analyze exported PDF bytes, not just LaTeX source. Display extraction limitations.
2. Describe scores as our own estimates, not an employer's ATS score, parser simulation, or hiring probability.
3. Never invent qualifications, employment, achievements, or numeric outcomes.
4. Preserve source before generated changes and reject stale proposals.
5. Record the supported compiler/package subset. Do not promise arbitrary Overleaf project compatibility.
6. Treat PDFs, filenames, logs, AI outputs, and client-reported results as untrusted inputs.

### Hosting and budget facts to account for

Render supports native Node and Docker deployment. Its free web services sleep after inactivity and use ephemeral local files; persist project data in the database. Free Render Postgres currently expires after 30 days, and dedicated background workers have no free instances. Accordingly, the first release has no always-on worker dependency. See the official references below.

Recommend Neon Free rather than Render's expiring free database. Neon's checked pricing advertises no payment card, no time limit, 1 GB storage and 100 CU-hours monthly per project. This is quota-limited hosting, not unlimited storage/compute; validate signup and the actual database connection in Part 0. Do not select a paid plan or trial.

AI inference needs its own provider access. Groq documents a Free tier and model-specific rate limits; evaluate it with synthetic code/resume fixtures before adopting a model. Treat rate-limit exhaustion as an unavailable feature, not permission to upgrade or charge. With no configured provider, editing, compilation, and deterministic resume checks still work.

### Compiler feasibility gate: Part 0A - compare server and browser execution

Neither server nor browser compilation has been tested in this repository. Docker is allowed. Benchmark a minimal server compiler on Render Free and the browser candidate before selecting the implementation. SwiftLaTeX documents WebAssembly PdfTeX/XeTeX engines, virtual input files, and package fetching. Its repository is AGPL-3.0. Check the actual engine/assets licenses and maintenance state before adopting it; do not infer obligations solely from a repository label.

The prototype must verify:

- At least two representative resume templates and a report, with required fonts, images, macros, Unicode, and references.
- Package/font availability, version pinning, redistribution permission, and delivery within the selected free hosts' limits. Do not depend on an uncontrolled package mirror at runtime.
- Vercel static-asset/deployment limits, download size, browser memory, cold/warm compilation time, and any required cross-origin isolation headers.
- Responsive UI, termination of infinite loops, cancellation, worker cleanup, and virtual-filesystem isolation between projects/users.
- A narrow host API: allowlisted package reads only, no arbitrary URL fetches or access to cookies, tokens, local storage, or unrelated project data. Web Workers have browser APIs; they are not automatically a security boundary by themselves.

**Server prototype:** test real templates with one compile at a time against Render Free's 512 MB RAM / 0.1 CPU budget, including API overhead, cold start, timeout, cleanup, and package/image build limits. Packaging TeX in a Docker service does not create a fresh sandbox per document. Prove untrusted files cannot read service secrets, reach arbitrary networks, or access other jobs; do not assume nested Docker or a host daemon is available. Keep test inputs synthetic and do not expose arbitrary public compilation before this is resolved.

**Gate outcome:** record whether server compilation passes capacity and isolation gates, whether browser WASM passes its gates, and select the demonstrated route. A browser fallback is acceptable when justified by measurements, not merely because Docker was previously disallowed. If neither passes, report the specific blocker and discuss scope; do not silently replace LaTeX with HTML-to-PDF or introduce a paid compiler.

## 4. Architecture, storage, and API boundaries

The diagram shows the browser execution option. If Part 0A validates server compilation, replace its compiler worker with an authorized API-to-compiler boundary and document the execution isolation. Do not infer that a Dockerized API can securely execute arbitrary user TeX in-process.

```text
Vercel: React/Vite static frontend
  |-- CodeMirror editor and PDF.js preview
  |-- Dedicated Web Worker: WASM LaTeX compilation
  |-- Dedicated Web Worker: bounded PDF extraction/checks
  |
  | /api/* via Vercel external rewrite (Vite proxy locally)
  v
Render Free: Node/Fastify API (Docker or native)
  |-- Better Auth sessions and project authorization
  |-- PostgreSQL: projects, files/assets, snapshots, reports
  |-- Bounded provider calls: AI proposals and job-match explanations
  v
Validated results returned to browser for review
```

### Cross-host authentication

Prefer same-origin browser requests to `/api/*`, externally rewritten by Vercel to Render. The rewrite is routing; business logic and credentials remain on Render. Validate this in Part 0B rather than assuming cross-site cookies between `vercel.app` and `onrender.com` will work in every browser.

Configure the auth public URL, trusted origins, secure host-only cookies, CSRF/origin checks, and any trusted proxy headers deliberately. Test sign-in, refresh, sign-out, password flows, multiple `Set-Cookie` headers, and direct unauthorized API access. Use an explicit preview-origin allowlist, not a wildcard for all Vercel deployments. Return `private, no-store` for protected responses and verify the rewrite/CDN does not cache user data. Avoid bearer tokens in browser local storage as a shortcut.

### Data and execution model

- Source/text, asset metadata, bounded asset bytes, snapshots, sessions, and saved reports persist in PostgreSQL. Set per-file/project/account limits and retention before accepting uploads.
- Compiled PDFs remain local unless the user saves a bounded snapshot/report. Validate saved PDF structure/hash and authorize every subsequent download.
- Record `snapshotId`, source/asset hashes, compiler build ID, and PDF hash. A browser-uploaded PDF is client-provided output, not server-attested proof it matches that source. Saved reports reference the exact analyzed PDF hash.
- Browser compiles have local states: loading/queued/running/succeeded/failed/timed-out/cancelled. Older results cannot replace a newer revision's preview. Browser close ends a compile; no promise of unattended completion.
- Keep initial server AI requests bounded by provider and proxy timeouts. Record request IDs, idempotency state, and results; report interrupted/expired requests accurately. Do not run a hidden queue or use artificial keepalive traffic to evade free-service sleep.
- Browser extraction/scoring results are user-document data, never authorization or billing evidence. Validate persisted schemas/evidence and record extraction/rules versions. No server authenticity guarantee is implied.
- Introduce an actual durable worker only if future requirements and an agreed hosting budget justify it; it must meet the same no-card and zero-subscription constraints, or receive new user authorization.
